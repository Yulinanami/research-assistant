**典型操作流程：** 创建项目并配置模型 → 上传文献/图片 → 选择解析方式与分块规则 → 检查、编辑或清洗文本块 → 生成领域标签和问题 → 生成单轮/多轮/图片问答 → 人工确认与 AI 评分 → 筛选导出 → 使用评测集检验模型表现。这是根据界面与代码梳理的流程，本次未执行实际操作。

**需要特别区分的能力边界：**

- **解析与原文预览：** Word 等资料主要转换为 Markdown 使用，不应描述为完整保留原文件版式的在线办公预览。表格 CSV 导入也不能替代 `.xlsx/.xls` 多工作表、合并单元格与数据类型解析。
- **清洗与去重：** 当前清洗服务直接用模型输出更新文本块。上传逻辑虽保存 MD5，但按 MD5 拦截重复文件的代码被注释，不能将其描述为已启用的文件去重，更没有证据证明具备语料级近重复去重与系统化隐私脱敏。[上传实现][C22]
- **来源关联与版本：** 文件—文本块—问题的数据关系有助于回查来源，但不是页码/坐标级引用，也没有提供发布后内容保持不变的数据集版本。现有修改和清洗主要更新条目，未发现生成新版本、版本切换和发布版本标记功能。[C6]
- **数据生产与知识库：** 支持为 RAG 准备资料和评测内容，不表示已实现向量检索、多篇论文的信息整理与关联、统一的概念索引或科研助手业务。

## 3.1.3 优势功能分析

### 优势功能1：根据文献生成问答数据集

- **功能描述：** 把领域文献上传、解析、分块、问题生成、答案生成、人工校对和训练格式导出安排在同一工作台，减少在多个独立工具之间转移资料的步骤。文本和图片具有各自的生成路径，并保留部分来源关联。
- **技术实现：** 文件转换与分块模块生成统一文本块；问题表关联块，答案生成时读取块内容；服务层通过统一模型客户端调用 LLM；数据表保存答案、模型、标签、确认状态等，导出模块完成训练格式转换。[C3]、[C5]、[C7]、[C19]
- **差异化价值：** 相比只提供文档解析或清洗算子的组件，其优势在于把加工结果直接接到可校对、可导出的 QA 数据生产界面。相比纯人工录入工具，能利用已有农业文献批量起草问答，但生成质量仍由模型和人工复核决定。
- **可借鉴方向：** 本项目的知识片段、问答对提取、问答标注和成果导出可参考这条操作流程。尤其可借鉴从答案回查原始片段、逐条修改后确认、仅导出确认条目的交互，再结合本项目的正式审核与版本要求完善成果管理。

### 优势功能2：按表达方式和阅读对象生成不同问答

- **功能描述：** 为同一文献设置不同表达方式和阅读对象，分别生成问题与答案；同时支持问题模板、自定义提示词和角色/场景化多轮对话，使数据构造不局限于一种问答表达。
- **技术实现：** `GaPairs` 保存文体和受众描述、启用状态；问题生成服务遍历启用组合，并将问题与组合关联，答案生成再加载对应组合。多轮服务基于来源片段和对话历史交替生成问题与回复。[C5]、[C7]、[C8]、[MGA 使用说明][S9]
- **差异化价值：** 相比简单复制或统一改写 QA，这一功能允许明确设置阅读对象和表达方式。对农业资料，可分别组织面向科研人员的专业解释与面向农业技术人员的操作问答。这里只说明可构造的形式，不将官方引用的其他论文性能提升数值当作本平台已验证效果。
- **可借鉴方向：** 可为本项目 SFT 增强提供可调整的生成条件，以及记录增强来源的方法。需同时核查增强前后农业术语、数值、条件和结论是否一致，不能仅以生成数量增加判断质量提高。

### 优势功能3：把数据质量检查与模型效果评价衔接起来

- **功能描述：** 数据条目可人工确认和 AI 评分；同一批领域资料还可生成评测题，再对模型进行自动评分或人工盲测。流程同时关注“数据是否可用”和“模型在这些知识上的表现”。
- **技术实现：** 数据质量服务将 QA 与来源片段送入评价提示词，保存分数和评语；评测数据表保存题型与标准答案；自动评测对客观题进行答案匹配、对主观题调用评分模型（Judge）；盲测接口保存两模型回答与投票结果。[C13]、[C14]、[C15]、[C16]
- **差异化价值：** 相比完成生成后立即导出，提供了继续筛选和比较的入口；自动评分和人工比较回答优劣适用不同题型。不过评分模型的偏差、标准答案准确性以及训练集与测试集重复问题仍需实际控制。
- **可借鉴方向：** 本项目可参考质量分与评语展示、按质量筛选、农业领域评测题构建、模型回答并排比较等设计。正式评测时应独立划分测试资料，避免把生成所依据的同一内容直接用于证明微调效果。

## 3.1.4 技术架构概述

- **整体架构：** Next.js 全栈应用，React/MUI 构建页面，`app/api` 提供 HTTP 接口，`lib/services` 处理业务，`lib/db` 访问数据。主要运行形态是单个 Node.js 应用，Electron 为同一应用提供桌面外壳。PDF、LLM 可通过接口调用外部或本地服务；未发现独立部署的一整套微服务体系。
- **核心依赖：** 本地 `package.json` 声明 Next.js 14.2.29、React 18、MUI 5、Prisma 6、Vercel AI SDK 4、LangChain 等依赖。实际数据库模型使用 **Prisma + SQLite**；文件、目录结构和部分配置存于 `local-db`。DOCX 转换使用 Mammoth/Turndown，PDF 基础转换使用 `@opendocsg/pdf2md`，复杂 PDF 接入 MinerU 或视觉模型。[C6]、[C23]
- **模型支持：** 统一客户端适配 OpenAI、OpenAI 兼容接口、Ollama、智谱、OpenRouter、MiniMax、阿里百炼等提供商；支持普通生成、流式对话和视觉输入。Ollama 或本地兼容 API 可用于本地模型接入，平台自身不提供模型训练或推理引擎。模型是否支持所需参数、视觉输入和输出结构仍须逐个核验。[模型客户端][C24]
- **扩展机制：** 提供项目级提示词、问题模板、分块参数、模型参数和 API 配置；源码中的提供商类、PDF 策略与服务函数可扩展。`app/api` 是应用内部业务接口，尚未看到稳定的通用插件 SDK、数据服务自动生成或企业统一接入约定。

**部署与集成注意点：** 主应用可以私有部署，但数据是否全程留在本地取决于模型接口地址和 PDF 解析方式。选择云模型或 MinerU 在线 API 时，资料会被送往配置的外部服务；要走本地流程，需另行准备本地模型和必要的 MinerU 服务。现有 SQLite 与本地目录适合独立工作台，不能由此推断满足本项目的多角色并发、统一存储与信创适配要求。

本地 `ARCHITECTURE.md` 仍包含文件系统模拟数据库、未来支持 PDF/版本管理等早期描述；本报告的架构判断以当前 `schema.prisma`、实际路由和服务实现为准。官方导出文档仍写有 Excel 和“Hugging Face 即将支持”，而当前界面和代码已提供 JSON、JSONL、CSV 导出及 Hugging Face 上传功能，说明文档与实现存在更新不同步的情况。[官方导出文档][S10]、[C19]、[C27]

## 3.1.6 与本项目的关系

### 可直接集成的能力

可作为组件候选的包括：文献转 Markdown 后的可配置分块、文本 QA 生成、图片 QA 生成、问题模板、QA 质量评分和训练格式转换。这些能力与 REQ-SJZS-033–038 的部分环节较接近，也可向科研助手的论文资料处理提供中间数据。

“可直接集成”在此表示值得进入选型验证，尚未验证无需改造即可接入。Easy Dataset 没有独立打包的完整企业数据加工 SDK；复制源码需要协议评估，接口集成需要确定数据格式、任务从创建到结束的状态和数据来源关系。本项目的账号、权限、审核、版本等管理要求还需在本项目侧实现或接入现有体系。

### 可借鉴的设计理念

- **以加工步骤组织工作台：** 文献与图片入口、问题管理、成果管理和评测分别提供页面，用户能看到加工过程与中间结果。
- **人机协作处理成果：** 模型负责起草，用户逐条查看、编辑、确认；导出时可只选确认条目，降低误把未检查内容交付的概率。
- **让生成规则可配置：** 分块大小、问题密度、问题模板、角色场景和提示词都可调整，适合适配不同类型的农业资料。
- **按主题检查数据分布：** 领域标签和按标签均衡导出，便于发现某些农业主题的数据过多或过少。
- **把任务过程与调用消耗呈现出来：** 进度、错误、Token 和耗时便于掌握批量生成任务的运行情况。

### 本项目相对优势

以下对比是**本项目需求设计的覆盖范围**与 Easy Dataset 当前源码的比较，不代表本项目已经实现或经过验收。

| 本项目规划的能力 | Easy Dataset 当前边界 |
| --- | --- |
| 数据需求、质量要求、来源授权、类型与量级规划（013–021） | 有项目与模型/提示词配置，缺少完整的数据建设前置规划表单及流程。 |
| 土壤场景清洗标准、数据字典与元数据规范（004–006） | 面向文献与 LLM 数据，未发现农业结构化数据的字段规范、单位/异常值校验和标准清洗流程。 |

### 本项目相对短板

Easy Dataset 已提供实现代码，而本项目当前需求尚未单独说明以下功能：按表达方式和阅读对象扩充问答、多轮角色/场景对话数据构建、按主题直接生成问答、按标签均衡导出、两模型人工盲测，以及 LLaMA Factory/Hugging Face 的专门衔接。

这些功能可作为比较和交互参考。其中按主题直接生成的内容缺少原文依据，对科研数据尤其需要谨慎评价；它们是否进入本项目建设范围，应由业务需要决定，不能因为开源平台具备就自动扩充需求。

## 3.1.7 调研结论

| 评估项 | 结论 |
| --- | --- |
| 推荐集成/借鉴程度 | **借鉴：高；直接集成：中。** 文献到 QA、图片问答、人机校对、数据增强和模型评价的交互与流程参考价值较高。源码或接口集成还需解决许可证、接口边界及实际样本验证；不宜直接作为全部数据管理与共享服务的实现依据。 |
| 技术成熟度 | **中。** 已有多平台发布、较完整的页面/服务/数据模型，功能范围覆盖多类 LLM 数据集和评测。当前仍有文档更新不同步及从源码中发现的实现问题；本次没有处理准确率、吞吐量、并发、断点恢复的实测证据。 |
| 社区活跃度 | **低（近期开发维护）；历史关注度较高。** 约 1.5 万 Stars，但近三个月默认分支无新提交，最近正式发布为 2026-04-09，抽查 Issue 缺少公开评论。关注人数不能代替当前维护响应。 |
| 一句话总结 | **Easy Dataset 适合借鉴农业领域文献与图片的问答数据集生产、审核和评测流程；本项目的数据标准、专用清洗、版本、权限与审批仍需独立规划和验证。** |

### 调研依据与待验证事项

本次已核对模板字段、核心页面与服务实现、模型和文件处理路径，并以官方在线信息补充时效性数据。实际体验与截图尚未完成，因此本报告是一份**源码与官方资料调研报告**，不能作为部署试用或功能验收记录。

后续实际体验的重点是：含表格/公式的农业论文与扫描 PDF 的解析效果；DOCX 复杂内容转换；中文文本分块后的信息完整性；问答与 MGA 增强中的是否保留原有事实；图片描述/问答质量；人工确认、导出、评测流程是否连续可用。本次没有测量这些指标，也未借用官方截图充当实测截图。

此外，标准问题生成服务 `generateQuestionsForChunk` 引用了未在该函数中定义的 `primaryGaPair`，批量 API 的非 GA 分支仍有调用；当前主要任务入口使用另一个 `generateQuestionsForChunkWithGA` 路径。这是静态发现的潜在运行问题，不能推断所有问题生成入口均不可用，也未在本次调研中修改。[C5]、[批量接口][C25]
