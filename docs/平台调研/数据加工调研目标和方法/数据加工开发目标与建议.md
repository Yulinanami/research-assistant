结合《科研助手平台+数据知识加工平台_需求规格说明书V2.0》，这份文档呈现了一个典型的“政企/科研机构私有化交付 + 源码级验收 + AI全链路闭环”项目。其中，**数据知识加工平台**承担了为整个科研体系（尤其是农学、生态学等垂直领域）生产高质量 RAG 知识切片与 SFT 微调数据集的核心底座职能（涵盖 REQ-SJZS-001 至 REQ-SJZS-044 共 44 个细分需求项，对应招标 35 个二级功能点）。   

针对该平台的**开发建设**与**同类项目技术调研**，以下梳理出一套可直接用于架构设计、排期与团队分工的**目标体系与执行方法论**。

### 一、 核心目标设定（Goals）

#### 1. 平台开发目标：打造“可交付源码、可拼插算子、AI原生驱动”的数据工厂

- **合规与交付硬性达标（首要目标）：** 100% 覆盖招标追溯矩阵中的 35 个二级功能点（REQ-SJZS-001 ~ 044），满足带“▲”核心条款——**交付全部源代码与完整工程文档（REQ-SJZS-044）**，并完成容器化（K8s）与国产信创环境适配。   
- **流水线标准化与向导化：** 将原本割裂的脚本工具串联成一条强引导的 Web 流水线（REQ-SJZS-011）：`数据需求定义 → 数据规划 → 多源采集 → 预处理（解析/清洗/切片/QA合成） → 人机协同标注与代码质检 → 模型评测 → 资产审批与API发布`。   
- **LLM 原生赋能（区别于传统大数据平台）：** 将底座大模型（Qwen3-235B/32B、DeepSeek-V3）深度嵌入加工链路（REQ-SJZS-012），实现五大智能节点：**自动生成数据集描述、基于文档自动提取/增强 SFT 问答对（REQ-SJZS-034/035）、LLM 预标注（REQ-SJZS-036/037）、自然语言生成质检代码并执行（REQ-SJZS-038）、自动化模型评测（REQ-SJZS-040）**。   
- **农业垂直领域壁垒落地：** 落实“土壤环境等典型场景的多源数据标准化清洗流程”（REQ-SJZS-006）及农业标准字典（GB/T、NY/T 等，REQ-SJZS-005），使平台不仅能洗通用文本，还能洗科研实验表格与专业文献。   

#### 2. 类似项目调研目标：寻找“开源可商用底座”，避免重复造轮子

由于本项目要求**交付全部源代码**（不能直接依赖闭源商业 SaaS，也不能只做简单的 iframe 嵌套导致二次开发受阻），调研的核心目标是：   

- **开源协议合规筛查：** 锁定采用 Apache-2.0 或 MIT 等宽松开源协议的组件，或明确核心算法引擎（Python Worker）与自研业务中台（Java/Go/Python Web）的解耦边界。
- **技术选型降本增效：** 为文档深度解析、分布式算子清洗、SFT 合成与增强、人机协同标注、模型评测这 5 大高难度模块找到成熟的开源内核，将自研精力集中在**统一工作流编排、权限审批、版本控制与前端交互**上。

#### 2. 科学执行调研的四个实操方法

1. **建立“招标需求-开源算子”映射表（Gap Analysis）：**

   将 SRS 中的 44 项需求逐条拆解，标记为三类：`A类（开源现成可用，只需包一层 API）`、`B类（开源有类似逻辑，需二次改造，如土壤清洗流程）`、`C类（纯业务管理流，如数据需求表单、数据规划、审批下载，需从零写 CRUD）`。

2. **搭建真实科研语料 Benchmark 进行 PoC 压测：** 准备 20 篇真实的农学/生态学中英文 PDF 论文（含三线表、折线图、化学分子式/公式）和 2 份土壤采样 Excel 表，分别跑通 MinerU 和 Docling，实测解析耗时、显存占用和表格还原度，为硬件算力规划提供依据。   

3. **逆向拆解优秀开源项目的 Prompt 资产：** 针对 `REQ-SJZS-034（问答提取）`、`REQ-SJZS-035（SFT增强）` 和 `REQ-SJZS-038（自然语言生成质检代码）`，直接拉取 `EasyDataset`、`Distilabel` 的源码，提取并汉化其内置的 System Prompt，结合农业领域术语进行调优。   

4. **信创与离线部署验证：** 提前确认目标环境的 CPU 架构（如鲲鹏 ARM64 或海光 x86）及国产 GPU（如昇腾 Ascend 或天数/沐曦等）对 PyTorch、MinerU 依赖的 OCR 模型（如 PaddleOCR/YOLO）以及向量数据库的兼容性。   

### 三、 数据知识加工平台的开发方法与架构设计建议

为了让平台既能快速交付，又能与兄弟子系统“科研助手平台”无缝打通，建议采用以下开发策略：

#### 1. 核心架构设计：控制面与计算面分离（Control Plane vs. Data Plane）

数据加工平台既有高并发低延迟的 Web 交互（列表查询 ≤ 2秒，逐条预览 ≤ 1秒），又有极重度的后台计算任务（几百页 PDF 解析、几万条 QA 大模型批量生成）。   

- **业务控制面（Web Backend）：** 使用 Python (FastAPI) 或 Java (Spring Boot) 构建，负责用户权限（RBAC/ABAC，REQ-SJZS-042）、数据需求与规划表单（REQ-SJZS-013~021）、数据集目录与审批流（REQ-SJZS-008~010）、以及 API 网关动态路由（REQ-SJZS-043）。   
- **异步任务调度与数据计算面（Task Workers）：** 引入 **Celery / Ray + Redis/RabbitMQ** 消息队列。所有的 PDF 解析、Data-Juicer 清洗、LLM 批量预标注、模型评测全部作为异步 Job 执行，通过 WebSocket/SSE 向前端实时推送进度条与运行日志（满足 6.7 界面需求）。   
- **统一模型网关（LLM Gateway）：** 使用 **LiteLLM** 或 **OneAPI** 统一封装底层的 Qwen3-235B、DeepSeek-V3、Qwen3-32B 以及多模态视觉模型（VLM）。这样无论是 `REQ-SJZS-001` 的模型试用 Chat Box，还是标注环节切换“默认模型/自定义模型（REQ-SJZS-036）”，都只需调用统一的 OpenAI 兼容接口。   

#### 2. 重点/难点功能模块的工程实现巧思（巧过验收）

- **难点一：自然语言生成质检代码并运行（REQ-SJZS-038）**
  - **需求痛点：** 用户输入一句自然语言（如：“检查所有回答是否少于 50 字，且不能包含‘根据文档’四个字，同时土壤 pH 值必须在 3.5 到 9.5 之间”），系统需由大模型生成质检代码并运行展示结果。   
  - **实现方法（沙箱 + 模板约束）：** 严禁让大模型随意生成完整的系统脚本直接 `exec`。应设计一个标准的 Python 质检函数签名模板 `def validate_row(row: dict) -> tuple[bool, str]:`，Prompt 强制要求大模型只生成函数体内的校验逻辑；后端在受限沙箱（如 `RestrictedPython` 或轻量容器）中遍历当前版本的数据集（Pandas DataFrame），捕获每行的 `(是否通过, 错误原因)`，并在前端表格中高亮标红未通过的样本。
- **难点二：数据集多版本控制与血缘追溯（REQ-SJZS-039 & 7.2 数据架构）**
  - **需求痛点：** 原始文档与问答对分别展示，每次执行 QA 提取、数据增强、人工审核都要生成新版本，支持切换查阅与标记发布版。   
  - **实现方法（写时复制 / 快照表设计）：** 不必引入笨重的 Git LFS。在关系型数据库（MySQL/PostgreSQL）+ 对象存储（MinIO/S3）中，设计 `dataset_id` -> `version_id (v1, v2...)` 的两级结构。当从 v1 触发“SFT问答对增强”生成 v2 时，创建一条新的版本元数据记录（记录父版本 `parent_version=v1`、操作类型、使用的 Prompt 和模型），并将新生成的条目写入带 `version_id` 分区的明细表或独立 Parquet/JSONL 快照文件中，即可极速实现版本切换对比与秒级分页预览（≤ 1秒）。   
- **难点三：数据集 API 自动生成与发布（REQ-SJZS-043）**
  - **需求痛点：** 数据集发布后，自动生成标准化接口，支持访问控制、限流、日志审计。   
  - **实现方法（动态路由网关）：** 无需为每个数据集动态编译部署新服务。编写一个通用的 RESTful 路由（如 `GET /api/v1/datasets/{dataset_code}/records`），当数据集状态变更为“已发布”时，自动为申请通过的用户签发 `API_KEY`；请求到达时，中间件校验 `API_KEY` 的权限配额（基于 Redis 令牌桶限流）并记录审计日志，直接查询已发布版本的快照数据返回。   
- **难点四：与“科研助手平台”的底座复用**
  - 规格书中，科研助手平台的 `4.3 文献摘要`、`4.6 LLM原生论文知识库` 与数据加工平台的 `5.8 数据预处理（PDF解析、切片）` 底层技术高度重合。**开发时务必将“文档解析服务（MinerU）”和“大模型推理网关”下沉为两个子系统共用的公共基础微服务**，一套代码同时支撑两边的验收，节省至少 30% 的开发工作量。   

#### 3. 分阶段迭代研发路线图（建议 4 阶段推进）

1. **阶段一：底座搭建与核心解析打通（M1）**
   - 完成 K8s 基础环境、MySQL、MinIO、向量库及大模型推理接口（OneAPI/vLLM）联调。   
   - 率先打通 `模型实验室 (5.1)` 与 `数据预处理中的 PDF/Word/Excel 解析 (5.8)`，因为这是后续一切知识库和问答生成的数据源头。   
2. **阶段二：数据全生命周期正向主链路贯通（M2）**
   - 开发 `数据需求 (5.5)` → `数据规划 (5.6)` → `数据采集 (5.7)` → `知识切片与 QA 提取/增强 (5.8)` → `问答/图像标注与版本控制 (5.9)` 的核心闭环，实现一条数据从上传到生成多版本 SFT 数据集的完整流转。   
3. **阶段三：高阶智能特性与农业垂直场景注入（M3）**
   - 实现 `自然语言生成质检代码沙箱 (REQ-SJZS-038)`、`文本清洗算子编排与土壤数据清洗流程 (REQ-SJZS-006/028)` 以及 `模型评测模块 (5.10)`。   
   - 完成 `数据标准规范与大屏指标看板 (5.2)`、`数据集概览广场、审批流与动态 API 服务 (5.3 & 5.11)`。   
4. **阶段四：信创适配、性能压测与验收文档交付（M4）**
   - 针对并发（≥10人）、列表查询（≤2秒）、逐条预览（≤1秒）、大文件分片断点续传进行专项优化。   
   - 整理源码仓库，输出第 9.3 节要求的 9 大类交付文档与需求追溯矩阵验收测试用例。
