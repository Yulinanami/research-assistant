将企业内部的业务文档（如 PDF 手册、Word 规范、客服日志、内部 Wiki）转化为高质量的 SFT（监督微调）数据集，本质上是一个“解析清洗 → 语义切片 → 强模型蒸馏合成 → 质检过滤 → 格式打包”的工业化流水线。

在 SFT 阶段，**数据质量远比数量重要**（经典的 LIMA 论文早已证明：1,000 条极高质量、风格统一的指令数据，效果远胜 5 万条粗糙拼凑的数据）。以下是完整的工程落地流程：

## 核心实施流水线

**1.文档解析与清洗（转化为干净的 Markdown）：**直接用粗糙解析器读取双栏 PDF 会导致段落错乱，使后续生成的问答产生严重幻觉。

原始业务文档中充斥着页眉页脚、水印、乱码表格和扫描图片。第一步不是直接切分，而是将所有异构文档统一转化为**结构化的 Markdown**（保留标题层级 `#`、`##` 和完整的 Markdown 表格）。

- **开源工具选型：** 优先使用 **MinerU**、**Marker** 或 **Docling** 处理复杂 PDF（支持双栏排版还原、跨页表格拼接和公式识别），避免使用传统的 `PyPDF2` 硬抽文本。
- **规则清洗与脱敏（PII Scrubbing）：**
  **正则过滤：** 剔除连续空白符、乱码控制符、HTML 残余标签、目录页（如 `...... 12`）以及无意义的免责声明。
  **隐私脱敏：** 用正则或 Microsoft Presidio 将真实客户姓名、手机号、身份证号、内部 IP、密钥替换为标准占位符（如 `<USER_NAME>`、`<PHONE_NUMBER>`），防止微调后的模型在对外服务时泄露隐私。

**2.基于文档结构与语义切片（Semantic Chunking）：**切忌按固定字数（如每 500 字）一刀切，否则会把核心条件与结论劈成两半。

为了让教师模型（Teacher LLM）基于文档生成准确的问答，每次喂给它的文本块（Chunk）必须具备**完整的上下文语义**。

- **按 Markdown 标题层级切分：** 先按 `# 一级标题 -> ## 二级标题 -> ### 三级标题` 进行树状切分，保证同一个小节的业务规则留在同一个文本块中。
- **面包屑注入（Context Injection）：** 这是防止数据脱离背景的关键技巧。如果某个三级标题下只有一句“*逾期超过 3 天将扣除 5% 保证金*”，直接切片会丢失主语。需要在每个文本块头部自动拼接它的父级标题路径：
  `【文档路径：供应商管理规范 > 违约处理 > 交货延迟】逾期超过 3 天将扣除 5% 保证金...`
- **长度控制：** 单个语义块通常控制在 **500 ~ 1,500 Tokens** 之间，兼顾信息密度与教师模型的注意力焦点。

**3.基于强模型的指令合成与扩增（Data Synthesis）：**SFT 的核心环节：用顶尖大模型（如 Gemini 2.5 Pro / GPT-4o / DeepSeek-R1）作为教师模型生成问答对。

人工手写几千条问答成本极高且风格不一。工业界主流做法是采用 **Self-Instruct（自举合成）** + **Evol-Instruct（指令演化）**。

- **多角色与多题型生成（Seed Synthesis）：** 将上一步的文本块放入 Prompt，要求教师模型扮演**不同业务角色**（如：挑剔的客户、刚入职的新员工、风控审核员）提出问题，并严格依据文本块生成回答。题型应覆盖：
  **事实问答与故障排查**（“遇到报错码 E402 怎么处理？”）
  **结构化信息抽取**（“把这段合同里的甲乙双方违约责任提取成 JSON”）
  **业务文案与邮件起草**（“根据这条退货规则，写一封安抚拒绝客户退款申请的回复”）
- **指令演化（Evol-Instruct 升维）：** 初次合成的问题往往太死板（像课本课后题）。需要让教师模型对问题进行二次改写：
  **口语化/模糊化：** 把“请简述 A 产品的退保流程”改写为“我昨天刚买的那个 A 险种不想要了，怎么退钱？会扣手续费吗？”
  **增加约束条件（深度演化）：** 增加多重业务条件组合，测试跨段落逻辑推理。
- **注入“拒答样本”（Negative / Refusal Samples）：** 专门生成 **10% ~ 15%** 文档中**没有提及**的相关业务问题，并强制标准回答为：*“根据现有的《XX业务手册》，暂未包含关于……的具体规定，建议您联系人工专员核实。”* 这能极大抑制微调后模型不懂装懂的幻觉。

**4.自动化质检、打分与去重（LLM-as-a-Judge）：**合成数据通常有 20%~30% 的废片率，严禁不经筛选直接送入训练。

合成出原始问答对后，必须通过三道筛子剔除劣质样本：

1. **格式与规则硬过滤：** 剔除 JSON 解析失败、回答过短（少于 20 字）、出现复读机式死循环、或者残留“根据您提供的文本块……”这种**暴露合成痕迹（Data Leakage）**的样本（需要用正则或提示词把“根据提供的文档”洗成自然的专业口吻）。
2. **LLM 裁判打分（LLM-as-a-Judge）：** 调用独立的裁判 Prompt，从三个维度对 `(Chunk, Question, Answer)` 打 1~5 分，**只保留全部 ≥ 4 分的样本**：
   **忠实度（Faithfulness）：** 回答是否 100% 源自原始文本块，有无私自编造数字或条款？
   **完整性（Completeness）：** 是否漏掉了关键的前置条件或例外情况？
   **指令遵循（Instruction Following）：** 语气、格式是否完全符合用户要求？
3. **Embedding 语义去重与多样性采样：** 使用向量模型（如 `bge-m3`）计算所有问题的向量余弦相似度。如果两条问题的相似度高于 **0.85**，只保留得分最高的一条，防止模型在重复问题上过拟合。

**5.格式转换与数据集配比（Format & Mixing）：**只用纯业务数据微调会导致模型“变傻”（灾难性遗忘），必须混入通用数据。

将质检合格的问答对转化为训练框架（如 **LLaMA-Factory**、**ms-swift** 或 **Axolotl**）支持的 **ShareGPT / OpenAI Messages JSONL** 格式，并完成最终配比：

- **黄金数据配比法则：** 建议采用 **70% ~ 80% 垂直业务数据 + 20% ~ 30% 高质量开源通用指令数据**（如 `ShareGPT`、`Infinity-Instruct` 中的通用逻辑、代码、日常对话样本）混合训练，防止模型丧失基础的语言理解与推理能力。
- **划分验证集：** 切出 **5% ~ 10%**（至少 200~500 条）不参与训练，作为评估集（Eval Set），用于监控训练过程中的 Eval Loss 是否过拟合。

## 核心工程资产：工业级数据合成 Prompt 模板

在实际跑批处理脚本（或使用 `Distilabel`、`Curator` 等合成框架）时，可以直接复用以下经过验证的 **System Prompt** 来驱动教师模型生成高质量 SFT 样本：

Markdown

```
# Role
你是一位资深的企业AI数据架构师与领域专家。你的任务是基于给定的【业务文档片段】，构建用于大语言模型监督微调（SFT）的高质量“指令-回答”数据集。

# Input Context
【文档归属路径】：{{breadcrumb_path}}
【业务文档片段】：
{{chunk_text}}

# Synthesis Rules (核心准则)
1. 绝对忠实（Zero Hallucination）：所有回答（assistant）必须严格依据【业务文档片段】中的事实、数字和逻辑，严禁依赖外部常识自行脑补未提及的业务规则。
2. 隐去拐杖词（No Context Leakage）：在生成的问题和回答中，严禁出现“根据上述文档”、“在提供的材料中”、“文中提到”等字样。请以该企业资深专家的自然口吻直接作答，仿佛这些知识已经内化在你的大脑中。
3. 提问多样性（Diverse Personas）：请生成 3 组不同视角的问答：
   - 类型 A（具体场景咨询）：模拟真实用户或一线员工遇到的具体业务情况，提问方式要自然、口语化。
   - 类型 B（复杂逻辑/多条件）：涉及流程步骤、例外情况对比或表格数据计算的深度问题。
   - 类型 C（边界拒答训练）：提出一个与该主题高度相关、但【业务文档片段】中确实未规定细节的问题，回答需礼貌说明当前规范未覆盖该情况，并给出合理的转交或核实建议。

# Output Format
请严格输出合法的 JSON 数组格式，不要包含任何额外的解释说明：
[
  {
    "type": "场景咨询 | 复杂逻辑 | 边界拒答",
    "messages": [
      {"role": "system", "content": "你是XX企业的智能业务助手，请专业、准确地解答业务与流程规范问题。"},
      {"role": "user", "content": "..."},
      {"role": "assistant", "content": "..."}
    ]
  }
]
```

## 动手落地的开源工具栈推荐

如果你准备在本地或服务器上搭建这套流水线，无需从零手写所有代码，可以直接组合目前最成熟的开源组件：

| **环节**            | **推荐开源工具 / 框架**          | **核心优势**                                                 |
| ------------------- | -------------------------------- | ------------------------------------------------------------ |
| **1. 文档解析**     | **MinerU** / **Docling**         | 专为大模型语料清洗设计，对中文复杂排版 PDF、跨页表格、公式转 Markdown 的准确率极高。 |
| **2. 合成与演进**   | **EasyDataset** / **Distilabel** | `EasyDataset` 提供可视化 Web 界面，上传文档即可自动切片、合成问答并导出；`Distilabel`（Argilla 出品）适合大规模 Python 批处理合成与打分流水线。 |
| **3. 人工抽检标注** | **Argilla** / **Label Studio**   | 训练前建议人工抽检 5%~10% 的数据。`Argilla` 专为 LLM 数据集设计，支持快速浏览和修改 `messages` 和偏好对。 |
| **4. 一键微调训练** | **LLaMA-Factory** / **ms-swift** | 导入上述生成的 `.jsonl` 文件，配置 `dataset_info.json` 即可零代码启动 LoRA 或全量微调。 |

> **实战避坑提醒（SFT vs RAG）：** 如果你的业务文档**每天都在频繁更新**（例如每日变动的价格表、实时库存），或者要求**一字不差地精准背诵上万条细则**，单纯靠 SFT 微调并不是最佳选择（因为模型权重很难精准记住海量动态长尾事实）。最稳健的工业架构是：**用 RAG（检索增强生成）负责实时查找原文档，用 SFT（指令微调）训练模型学会“如何阅读检索出来的业务文档并按公司规定的格式、语气回答”**。
